# 拾言（Shiyan）MVP PRD

状态：已完成产品问答，作为拾言当前 MVP 的产品需求基线

日期：2026-08-29

唯一真相目录：`docs/shiyan/`

> 本 PRD 定义拾言的产品问题、用户场景、功能范围、交互规则与验收标准。具体 API、表结构、库选型、音频切片与部署细节由实现侧依据稳定性、落地成本与 Debug 成本决定，不在本 PRD 中固化。

## 1. 产品背景

高强度工作下，冗长会议很难完全避免。真正造成负担的不是“会议存在”，而是会后还需要重新听、重新整理、重新复制粘贴，再把信息落到工作系统中。

拾言要解决的问题是：

> 会议可以很长，但会后的整理、提炼与落地必须足够快。

拾言不是录音机，也不是单纯的 STT 工具。它是 Mira 的官方内置生产力插件，负责把长会议或口述内容快速收敛成可执行信息，并让用户在确认后投递到真实工作载体。

## 2. 产品目标

MVP 目标：跑通一条用户真实愿意在工作中使用的闭环。

```text
选择场景
  -> 录音采集
  -> 结束后确认标题 / 场景
  -> 提交处理
  -> STT 转写
  -> AI 整理 / AI 调整
  -> 回显原文与整理稿
  -> 用户最终编辑
  -> 分享 / 投递
```

核心价值：

1. 快速提炼：不用重新听完整会议。
2. 快速整合：把决策、需求、TODO、风险等收敛成清晰结构。
3. 快速落地：确认后直接进入 GitHub 等工作载体，减少二次搬运。

## 3. 目标用户与产品策略

MVP 先服务真实 dogfood 场景，以高强度工作中的会议与口述为主要验证环境。

产品策略：

- 先把自己用顺，再自然推广给其他 Mira 用户。
- Mobile First，但不是 Mobile Only。
- Mobile 是优先采集端。
- Desktop 始终是一等客户端，长期承担更完整的回看、调整、配置与历史使用。
- 首版作为 Mira 官方内置插件。
- 架构保留未来第三方插件扩展能力，但插件市场与第三方生态不属于 MVP。

## 4. 场景模型

拾言采用“轻量内置 + 自定义场景”的分类方式。

首版场景优先级：

1. 会议采集。
2. 临时口述需求。
3. 个人复盘 / 想法记录。

其中会议采集是 MVP 第一场景，其他场景复用同一条“采集 -> 转写 -> 整理 -> 调整 -> 投递”链路。

### 4.1 内置场景

内置场景由 Mira 提供默认整理结构和提示策略，用户无需配置 Prompt 即可使用。

会议场景至少应支持整理：

- 摘要
- 关键决策
- 待办事项
- 风险 / 阻塞
- 待确认问题

### 4.2 自定义场景

MVP 的自定义场景仅开放：

- 场景名称
- 整理要求
- 输出结构

MVP 不直接向普通用户开放完整 Prompt 编辑，以降低配置和 Debug 成本。

## 5. 核心用户流程

### 5.1 开始采集

用户从 Mira Mobile 的生产力插件区域进入“拾言”，选择场景后开始录音。

MVP 不要求实时字幕，不要求边录边转写。

### 5.2 结束录音

用户点击结束后，不立即自动提交。

必须先进入轻确认步骤：

- 确认 / 修改标题
- 确认 / 修改场景
- 提交处理

用户确认后才进入后台处理流程。

### 5.3 后台处理

提交后，用户无需停留在当前页面等待完整处理结束。

任务需明确展示当前阶段，例如上传、转写、整理、待调整、投递等。

任何单一阶段错误不得粗暴显示为“整个任务失败”。已完成阶段及产物必须继续有效并可恢复。

### 5.4 回显与调整

处理完成后，拾言至少回显两层内容：

1. Transcript：原始 STT 转写结果。
2. AI Draft：AI 整理后的结构化内容。

规则：

- Transcript 是证据层，长期保留。
- Transcript 在 MVP 中只读，不允许直接修改原始转写。
- AI 可以在用户最终编辑前反复整理或调整。
- 用户进入最终编辑后形成 Final Draft。
- Final Draft 不得被后台 AI 自动覆盖。
- 若未来在 Final Draft 后再次调用 AI，应产生新的候选结果，而不是静默覆盖人工内容。

### 5.5 原文定位

MVP 只要求能够查看完整 Transcript。

“从摘要 / 决策 / TODO 跳回对应原文或录音时间点”属于 MVP+1，不阻塞首版验收。

### 5.6 分享与投递

分享与投递是两个概念：

- 分享：把当前 Final Draft 临时导出或发送给他人。
- 投递：把 Final Draft 落到长期工作载体。

MVP：

- Markdown 导出 / 系统分享。
- GitHub 作为第一优先 Destination。

后续：

- PDF：MVP+1。
- Word：MVP+2。
- Notion：第二优先 Destination。
- 飞书、企业微信、微信等后续按 Destination Adapter 扩展。

投递必须基于用户确认后的 Final Draft，不允许 AI 初稿未经确认直接外发。

## 6. Destination 模型

场景决定“如何整理”，Destination 决定“整理后送到哪里”，二者必须解耦。

优先级：

1. GitHub
2. Notion
3. 飞书 / 企业微信 / 微信等

### 6.1 GitHub

默认内容仓库：`dangjingtao/mira-shiyan`。

MVP 规则：

- 用户最终确认后直接投递正式 Markdown。
- 不在 GitHub 额外造一个待审核 inbox 流程。
- Git commit history 作为已投递内容的可信历史。
- 拾言不重复实现完整 Git 版本系统。

### 6.2 真相链接

历史任务中的“去向”必须优先保存真实可打开的 canonical link，而不是只显示“GitHub / Notion”标签。

例如：

- GitHub：最终 Markdown 文档 URL。
- Notion：最终 Page URL。
- 其他载体：如有稳定资源链接则保存真实链接；没有稳定链接时保存可追踪的资源标识。

投递失败时不得伪造去向。

## 7. 历史任务

拾言需要提供轻量历史任务列表。

每项至少展示：

- 标题
- 场景
- 创建 / 录制时间
- 当前阶段 / 状态
- 已投递时的真实去向链接

历史任务的主要价值：

- 查看仍在处理的任务
- 找到待调整任务
- 找到已经投递的结果
- 对失败阶段执行恢复或重试

## 8. 数据保留与隐私

### 8.1 原始录音

默认保留 3 天后自动删除。

用户应可以对重要录音选择“保留原始录音”，取消默认自动清理。

录音被删除后，不影响已经生成并保存的 Transcript、AI Draft、Final Draft 与 Delivery Record。

### 8.2 Transcript

Transcript 长期保留，作为可追溯的文字证据层。

Transcript 不因原始录音自动删除而同步删除。

## 9. 任务状态原则

拾言以 CaptureTask 为中心，而不是以录音文件或最终文档为中心。

一个 CaptureTask 可以拥有：

- 原始录音
- Transcript
- AI Draft
- Final Draft
- Export 结果
- Destination 投递结果

状态必须区分：

- 整个 Task 当前处于什么阶段
- 某个 Stage 自己是否成功 / 失败 / 可重试
- 具体错误是什么

禁止：任一阶段异常 -> 整个 Task 显示“失败”。

例如：

- STT 失败：录音仍可用，可重试 STT。
- AI 整理失败：Transcript 仍可用。
- GitHub 投递失败：Final Draft 仍可用，可重新投递。
- 导出失败：不得污染其它阶段。

## 10. MVP 明确不做

- Speaker diarization / 多人说话人区分。
- Speaker identification / 自动判断具体是谁。
- 实时字幕。
- 边录边转写。
- 自动拆任务卡。
- 自动生成 PRD。
- 自动判断需求变更并修改正式文档。
- 自动派发负责人。
- 完整第三方插件市场。
- 整理结果到原文 / 音频时间点的精确引用跳转。
- 完整 PDF / Word 导出体系。

## 11. 异常与恢复要求

MVP 至少覆盖以下异常：

- 录音中断
- App 进入后台或被系统终止
- 无网 / 弱网
- 上传失败
- STT 失败
- LLM 整理失败
- GitHub 投递失败

产品原则：

- 已保存的本地录音不得因网络错误丢失。
- 上传失败不得要求用户重新录音。
- 后续阶段失败不得让前面已经成功的产物失效。
- 可重试错误必须给出明确重试入口。
- 错误文案应尽量表达“哪个阶段出了问题”，而不是笼统的“任务失败”。

## 12. MVP 成功指标

MVP 验收基准：一段约 40 分钟的真实会议录音。

必须满足：

1. 从录音到最终投递完整闭环可用。
2. 会议结束后 5 分钟内进入可编辑整理稿。
3. 用户不需要重新听完整录音，也能完成最终确认与投递。
4. 弱网或单阶段错误下，不丢失原始录音和已经成功的中间产物。
5. 历史任务可以找到当前状态和最终真实去向。

## 13. MVP 验收场景

### A. 正常会议

- 录制约 40 分钟会议。
- 结束后确认标题与场景。
- 提交处理。
- 获得 Transcript 与 AI Draft。
- 用户调整 Final Draft。
- 投递 GitHub。
- 历史任务中可以打开真实 GitHub 文档链接。

### B. 上传失败

- 本地录音已经结束。
- 上传过程中网络中断。
- 任务显示上传阶段异常，而不是“整个任务失败”。
- 恢复网络后可以重试上传，无需重新录音。

### C. STT 失败

- 原始录音仍然存在。
- STT 阶段显示可重试错误。
- 重新执行 STT 后任务继续推进。

### D. AI 整理失败

- Transcript 保持可查看。
- AI 整理阶段可重试。
- 不重新执行已成功的 STT。

### E. Destination 失败

- Final Draft 已完成。
- GitHub 写入失败。
- Final Draft 继续可读、可编辑。
- 用户可以再次投递。

## 14. 后续方向

在 MVP 被真实工作场景验证后，再评估：

- 多人识别
- 原文 / 时间点引用
- PDF / Word
- Notion 完整投递
- 更多 Destination
- Desktop 完整工作台
- 自定义场景高级模式
- 第三方插件机制
- 基于历史会议的检索、对比与工作记忆

这些方向不改变当前 MVP 的验收边界。
